# Cross origin authentication

Please [refer to this page](../../pure-php/advanced-behaviours/cross-origin-authentication.md) to know more about the Cross Origin Authentication.

## Configuration

The configuration of the allowed domains can be done as follows.

```yaml title="config/packages/webauthn.yaml" linenums="1"
webauthn:
    allowed_origins:
        - 'https://acme.com'
        - 'https://acme.fr'
        - 'android:apk-key-hash://your-app-hash'
        - 'ios:bundle-id://your.bundle.id'
    allow_subdomains: true
```

!!! info

    **Changed in v5.3.3:** entries that are not URLs, such as `android:apk-key-hash:<base64>`, are compared verbatim with the origin sent by the client. Entries made of a host only are normalized to `https://`.

!!! warning

    **Deprecated in v5.4.0:** `allowed_origins` and `allow_subdomains` are removed in 6.0.0. Pass the list to `withAllowedOrigins()` and `withAllowSubdomains()` on the [verification helpers](../verification-helpers.md) instead. The node also publishes the [Related Origin Requests](#related-origin-requests) endpoint, which the helpers do not replace: keep it if your application relies on that endpoint. See [From 5.3 to 5.4](../../migration/from-v5.3-to-v5.4.md#webauthnallowed_origins-webauthnallow_subdomains).

## Ceremony origin pinning

!!! info

    **New in v5.4.0**

The allow list is checked against the union of its entries: any origin it contains is accepted for any ceremony. Origins sharing a Relying Party ID rarely share a trust level though, and an assertion obtained on the lowest-trust one (an XSS on a marketing site, a customer-provisioned subdomain) is replayable against the highest-trust one.

Ceremony origin pinning closes that window. The options request records the origin it was served on next to the challenge, and the response is then required to come from that very origin:

```yaml title="config/packages/webauthn.yaml" linenums="1"
webauthn:
    ceremony_origin_pinning: true
```

The option is the application-wide default of `WebauthnAttestationVerifier::withCeremonyOriginPinning()` and `WebauthnAssertionVerifier::withCeremonyOriginPinning()`, so a single endpoint can opt in or out. See the [Verification Helpers](../verification-helpers.md#configuring-the-ceremony) page.

The check is additive: the allow list still runs first, so pinning only narrows what is accepted.

!!! warning

    Pinning fails closed, which is why it is opt-in and defaults to `false`. A ceremony stored without an origin is rejected, which covers the options generated by a previous version of the bundle and still held in the cache during a deployment. Keep it disabled for native application facets (`android:apk-key-hash:...`) and for any flow whose options request and ceremony do not share an origin.

    An `OptionsStorage` of your own must keep the origin of each `Item` (`getCeremonyOrigin()`) and its scope (`getScope()`), and rebuild the item with `Item::create($options, $userEntity, $ceremonyOrigin)->withScope($scope)`. Otherwise every pinned ceremony is rejected, and the options lose the binding to the endpoint that issued them.

### Choosing what to put in the allow list

* List only the origins that share the trust level of the endpoint, and prefer several narrow lists, per controller or per verifier through the helpers, over a single broad one.
* Keep `allow_subdomains` to `false` whenever a subdomain can be controlled by a third party (customer-provisioned hostnames, user content, staging hosts). An assertion obtained on such a subdomain would otherwise be accepted on the high-trust origin.

## Top origin validation (cross-origin iframes)

When the ceremony runs in a cross-origin iframe, the client data contains the origin of the embedding page in a `topOrigin` field.

!!! danger

    **Changed in v5.3.4:** such a response is rejected unless a top origin validator is configured. Applications that do not use iframes are not affected, as a same-origin ceremony carries no `topOrigin`.

Write a service implementing `Webauthn\CeremonyStep\TopOriginValidator`:

```php title="src/Security/MyTopOriginValidator.php" linenums="1"
<?php

declare(strict_types=1);

namespace App\Security;

use Webauthn\CeremonyStep\TopOriginValidator;
use Webauthn\Exception\AuthenticatorResponseVerificationException;

final readonly class MyTopOriginValidator implements TopOriginValidator
{
    public function validate(string $topOrigin): void
    {
        $allowed = [
            'https://app.example.com',
            'https://dashboard.example.com',
        ];
        if (!in_array($topOrigin, $allowed, true)) {
            throw AuthenticatorResponseVerificationException::create(
                'The top origin is not allowed.'
            );
        }
    }
}
```

Then declare it with the `top_origin_validator` option:

```yaml title="config/packages/webauthn.yaml" linenums="1"
webauthn:
    top_origin_validator: 'App\Security\MyTopOriginValidator'
```

!!! info

    The option is an alias to your service. A service registered under the `Webauthn\CeremonyStep\TopOriginValidator` identifier, which autowiring does by default when a single implementation exists, is picked up without any configuration. The validator applies to both the creation and the request ceremonies.

A verification helper can use another validator for one endpoint with `withTopOriginValidator($validator)`, or disable the validation there with `withTopOriginValidator(null)`. See [Verification Helpers](../verification-helpers.md#configuring-the-ceremony).

See [the pure PHP documentation](../../pure-php/advanced-behaviours/cross-origin-authentication.md#top-origin-validation-cross-origin-iframes) for the built-in `HostTopOriginValidator` and more details.

## Related Origin Requests

When the `allowed_origins` parameter is set, the path `/.well-known/webauthn` is enabled. It returns the list as a JSON object, `{"origins": [...]}`, which the clients read to let the origins of other registrable domains use your Relying Party ID.

The clients only process the first five distinct eTLD+1 labels (registrable domains) of that list, and silently ignore the origins beyond.

!!! info

    **New in v5.4.0**

The bundle checks the published list when the cache is warmed up, and logs a warning naming the origins the clients will ignore. Nothing is refused: the endpoint still publishes the whole list. The check needs a service that resolves the public suffix of a host. The library provides `Webauthn\Util\PdpPublicSuffixResolver`, which adapts [`jeremykendall/php-domain-parser`](https://github.com/jeremykendall/php-domain-parser) (a suggested dependency, install it yourself):

```yaml title="config/packages/webauthn.yaml" linenums="1"
webauthn:
    allowed_origins:
        - 'https://acme.com'
        - 'https://acme.fr'
    related_origins:
        public_suffix_resolver: 'Webauthn\Util\PdpPublicSuffixResolver'
        label_limit_check: true # default
```

`PdpPublicSuffixResolver` takes a `Pdp\PublicSuffixList`: declare the service with the list your application loads, or implement `Webauthn\Util\PublicSuffixResolver` yourself. Without a resolver, no check runs. Set `label_limit_check` to `false` to disable it.
